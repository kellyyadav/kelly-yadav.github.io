Why a Kalman filter instead of a moving average?

GPS noise is not uniform. A Kalman filter keeps a running estimate of position and velocity and weights each reading by its uncertainty, so it damps jitter without lagging behind real turns.

  • Predict the next state from the last one
  • Update the estimate with the new reading, weighted by uncertainty
  • Compare each reading to the prediction to flag impossible jumps

Why WebSockets for battles?

Both players need to see battle state change live. A persistent connection pushes updates both ways, which suits a 1v1 better than repeatedly polling the server.

  • Matchmaking and battle status are pushed to both clients
  • Postgres stays the source of truth for profiles, questions and solves
  • Question generation runs behind a serverless route, so the key never reaches the browser
Trade-off I'm aware of: CaloriQ's current setup calls an AI API from the frontend, which exposes the key to users. The fix is to move those calls behind a serverless function, the same pattern CodeArena uses.
